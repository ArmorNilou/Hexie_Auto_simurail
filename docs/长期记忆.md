## 1. 铁律：不可违反（违反过的都见 VIOLATIONS.md）

| # | 铁律 | 具体含义 |
|---|---|---|
| 1 | **镜像归镜像、导航归导航** | ScheduleMirror 只负责把 Create 时刻表读成我们的游标；导航/驱动是另一层。两层不许互相塞逻辑。 |
| 2 | **不让 Create 决定运动** | 它的导航我们不用（不调 `startNavigation`/`startCurrentInstruction`）。`train.speed` 由 mixin 压 0，物理速度由 `TrainSpeedInjectMixin` 注入。**这条只约束"谁决定运动"，不约束"能不能碰它的状态"。** |
| 2b | **但它的状态我们可以直接改** | `Train`/`Carriage` 的 `invalid`/`derailed`、车厢 `TravellingPoint`、运行时字段——目标需要就直写、直调。**不需要它同意，也不需要走它的流程**。 |
| 3 | **不写 Schedule 对象** | 只通过 `AllDataComponents.TRAIN_SCHEDULE` 写 `CompoundTag`，绝不构造 `Schedule` 实例塞进去。 |
| 4 | **不用 `Navigation.findPathTo`** | 已判定：除 Create 自家车外基本没有可用性。路径规划是我们自己的活。 |
| 5 | **不用 TrackEdge 对象身份当链路身份** | `connectNodes` 为每段物理轨道造**两个有向 TrackEdge**。判断"同一段轨"必须用无序节点对（`RailCache.sameLink`）。 |
| 6 | **不把 `getLocationOn` 当归属检查** | 它对任何 edge 都返回一个数（`isPrimary(edge.node1) ? len-pos : pos`）。判归属只能用 `CreateApi.hostsPoint`。 |
| 7 | **到站判定自己判断**（2026-11-16 契约变更） | 解耦/虚拟车那套已删，没有消费者需要 Create 的边点回调。到站 = 弧长距站 `|d| ≤ ARRIVE_TOL` **且** `v < V_ARRIVE`，用我们自己的制动代码停住。**边点只用于信号**（`SignalBoundary` 是唯一可知渠道）。此条覆盖 `VIOLATIONS.md` 的 V4/V7/V8 —— 那是用户决定，不是回退。 |
| 8 | **到站不许 `train.speed = 0`** | 见 V8。停车靠输出抱闸 + 物理体自己停。 |
| 9 | **信号仍走边点**，到站不再走边点 | 信号没有别的可知渠道，必须用 `EdgePointWatch.probe` + `SignalProbe`；到站见铁律 7。两套判据**故意不同**，不要再"统一"。 |
| 10 | **不要乱兜底** | "这个兜底不可信"、"兜底一般都是闯祸"。规划失败就报失败，不许拿反方向/绕环/猜站点顶上。 |
| 11 | **只留一套实现** | 不做补丁式治症状；同一件事不许有两个并行的算法。 |
| 12 | **不猜，先看日志/代码再改** | 每改一处必须能指到日志证据或源码事实。 |
| 13 | **"单向"= 单端起点，不是物理单向**（2026-11-16 实测跑通） | 搜索只从**本车**出发（不再做"车正向 + 站准入端反向"两头对撞求 F∩T，那个做不出来）；但**两个初始方向同时入队**，岔口/支线随便走。车**可以往返跑**：路线要走反方向时换另一个驱动面（换向器反相）。**永远不要**把它理解成"车只能朝一个物理方向开"或"不试反方向"。 |
| 14 | **THROTTLE 是单向指令输出** | 输出给调度器外接转速器械，**不需要回馈闭环**。但必须**曲线加速**（随距离/时间平滑爬升），不许阶跃。 |
| 15 | **空频率也是信号** | Redstone Link 的空频率是合法频道，别当"没配置"。 |
| 16 | **Create 是数据源，不是权威** | 我们拿它的数据，是因为**我们算不出来**（轨道图节点/边几何、`TravellingPoint` 在边上的位置、边点、信号状态、时刻表结构）——**不是因为它更准**。同时它的状态机/导航流程对我们没有约束力：它不给我们做的（比如把车重挂回轨道），我们直接改它的东西自己做。 |

## 2. 已证实的 Create 6.0.10 API 事实（别再重查）

反编译手段：`C:\Users\PC\AppData\Roaming\.minecraft\runtime\java-runtime-delta\bin\javap.exe`，jar 在 `H:\hf\lib\create-6.0.10.jar`。

1. `TrackGraph.connectNodes` 给每段物理轨造**两个有向 TrackEdge**：`edgeA(nodeA→nodeB)` 进 `connectionsByNode[nodeA]`，`edgeB(nodeB→nodeA)` 进 `connectionsByNode[nodeB]`。
2. `getConnectionsFrom(n)` **只返回 `node1 == n` 的出边**；`putConnection` 只写一侧。**没有反向索引**。
3. `TrackEdgePoint.getLocationOn(edge)` 不检查归属（见铁律 6）。
4. `isPrimary(node)` 的真身是 `edgeLocation.getSecond().equals(node.getLocation())` ⇒ **站点的准入节点 = edgeLocation 的第二个节点**；驶入边 = `connections(edgeLocation.first).get(edgeLocation.second)`。
5. `TrackEdge.canTravelTo(other)` = `this.getDirection(false)·other.getDirection(true) > 0.875`（≈29°），**纯几何**。
6. `getDirection(b)` 两个 b 都返回**行进方向 node1→node2**（只是取样点不同）；反向通行必须取负。
7. `RedstoneLinkNetworkHandler` **没有 tick()**；强度只在 `updateNetworkOf` 被调用时重新广播；`IRedstoneLinkable.getTransmittedStrength()` 是拉取式的活值。
8. `Schedule.cyclic` 是 public boolean（原 `ScheduleMirror` 忽略它，现已读取）。
9. `SignalProbe.observe(SignalBoundary, TrackNode enteringNode, Train)` → `Obs(signal, group, primary, chained, state)`；`State ∈ {CLEAR, BLOCKED, UNKNOWN}`。
10. `Carriage.getLeadingPoint() / getTrailingPoint()`；单节车厢只跨一条边，车头/车尾是**方向相反的两个对象**。
11. **车头点定义"前进方向"：车头 `position` 增大 = 车在前进**（朝 `head.edge.node2`）。这条由 2026-11-16 20:05 日志反证过，见 §6。
12. 20 tick/秒；`driveTick` 决策周期 5 tick = 0.25 s。
13. **道岔 = `Train.manualSteer`（`TravellingPoint.SteerDirection`：NONE/LEFT/RIGHT）。** `Navigation.control(point)` 在 `destination==null` 时返回 `point.steer(train.manualSteer,(0,1,0))`，这是岔口**唯一**的决策通道；Create 没有 TrackSwitch、没有岔位状态。`manualTick` 是它的同伴（每个 tick 会被 `tickPassiveSlowdown` 自动清掉，得每 tick 重设）。全链路见 §6.7。
14. `Train.tick` → `Carriage.travel(level, graph, dist, prevCarriageTail, nextCarriageHead, which)`；`control()` **只**给本车最前那个点（`var31==null`，即 `carriages.getFirst().getLeadingPoint()`），其余点全是 `follow()`，跟着已走过的轨迹走。

## 4. 导航五步契约（设计契约，不可改顺序）

1. 按时刻表当前 entry → 缓存这一段：路线的有向边序列 + 沿途边点（站点/信号机：弧长 s、EdgePoint 对象、所在边）
2. 用缓存边点 + 物理车位置 → 双向沿途搜索 → 得到轨道集合
3. 判定目标相对车头的方向 + 距离 → 刷新 UI「距站」（只在到站段显示数字）
4. 驱动车辆（面锁存：认证一次后锁死，到站前不再换面）
5. 依据边点触发停车（信号机 / 到站）⇒ 停车后刷新导航（回到步骤 1）

约束：一站一站来；②③只读①的缓存，不另建路；**驱动层只读缓存，不规划，一段只规划一次**。

驱动阶段机：`行驶 → 滑车 → 刹车 → 到站`；循环/不循环由 `Schedule.cyclic` 决定（`myEntry` 只在 cyclic 时回绕）。

速度控制（两份共用**同一个**「曲线速度」，双向一致）：

```
a  = train.acceleration()
vT = max(0.4, min(V_CRUISE_MPS, sqrt(2a * max(0, d - 0.5))))
dv = vT - v
dv > +DV_BAND  → 加油门
|dv| <= DV_BAND → 滑车
dv < -DV_BAND  → 刹车 max(15 * (-dv) / DV_FULL, brakeFloor)      // 急刹也是递增的，不是摁死
```

制动/到站两条链**故意分开**：减速用缓存弧长 `d = route.stationS - sNow`；到站用 Create 原生边点监听，窗口 `max(0.6, v*0.25 + 0.5)`（必须覆盖一拍行程，否则高速整帧跳过）。
到站需 **边点命中（对象身份 `atPoint.point == route.target`）+ `v < V_ARRIVE`** 同时成立；高速命中只重刹不latch。
`d < 0` ⇒ `holdOutputs()` + 警告「已越过目标站 X 米，抱闸停住」，不许油门蠕动。

## 6. 站 4 段 `sNow=NaN` 死循环（已实现修复：改成面标定定方向，待实测）

### 现象（20:05 日志，entry=1 → target=4）

```
t=2   行驶中 d=93.5  v=0.57 throttle=2
t=4   行驶中 d=94.1  v=1.86 throttle=4
t=6   滑车   d=95.3  v=2.88
t=8   行驶中 d=96.8  v=2.79 throttle=1
t=10  滑车   d=98.2  v=2.93
[drive] 新段 target=4 entry=1 | ok backwards=true 距站=98.2 边数=7
[drive] 车位不在缓存路线里 sNow=NaN stationS=98.18604737999658 → 重规划   ×649（约 162 秒）
```

车停在原地：`spd=0.000`、输出全程中性、末尾 `[diag] edgeLen=1.0`（开局是 `edgeLen=16.0`）。

### 根因 A（主因）：规划选了**反方向**

`RailSearch.search()` 第 152-160 行：从车头朝 node2 搜一次、从车尾朝 node1 搜一次，**谁短用谁**。
这两个方向对单向车是**互斥**的，不能比长短。站 4 段车尾那次赢了 ⇒ `backwards=true` ⇒ 整条路线 s 轴与车实际前进方向**相反** ⇒ 车一前进 `sNow` 就变小 ⇒ `d` 单调增大（日志正是 91.5→98.9）⇒ 车头走出第一条边、进到不在 `legs` 里的那条 1 m 小边 ⇒ `legOf()=null` ⇒ `sOf` 返回 NaN。

**这就是"规划方向必须等于车的真实前进方向（车头朝 node2）"的实证**，也说明 `backwards=true` 的路由本身就是"倒着开"，对单向车一律不合法。

### 根因 B：`driveTick` 第 1241 行把点覆盖掉了

```java
1219|  TravellingPoint pt = this.routePoint(train);   // 按"哪个能映射进路线"选
1241|  pt = CreateApi.leadPoint(train);              // ← 规划完这一拍硬写回车头
1248|  double sNow = route.sOf(pt.edge, pt.position);
```

只要该段是 `backwards=true`，1241 就把 `pt` 换成车头点，`sOf` 立刻 NaN → `driveResult = null` → 下一拍重规划 → 又 NaN。**649 对 `新段`/`重规划` 就是这么来的**，而且 `neutralOutputs()` 让车一点牵引都拿不到。

### 改法（最小、不兜底）

1. `RailSearch.search()` 只按**一个方向**展开（方向由面标定给出，不再从两端挑短的）；搜不出来就 `Result.fail(原因)`，不许拿反方向顶上。**已实施，见 §6.1。**
2. `driveTick` 里 `pt` 全程用**车头点**（`routePoint` 已删），并删掉规划后覆盖 `pt` 的那一行。**已实施。**
3. 保留 `d < 0` ⇒ 抱闸报错（单向行驶下越过站就是真故障，必须叫出来）。

验收标准：`d` 从 91.5 一路**减小**，站 4 触发 `抓到边点 … 是目标=true`。

### 6.1 已实施（2026-11-16 20:24，jar 168,716 字节；等实测验收）

方向不再由搜索"挑"，改由**面标定结果**决定。三处改动：

**① `RailSearch`：先验两道，再按标定方向搜一个方向**

原来那两个方向（朝 node1 / 朝 node2）**不是用来比长短的**，它们的职责是**校验**：
> 目标车站名字必须与时刻表导航一致 + 进入方向必须与可用轨道一致，然后才允许沿 node1 或 node2 出发。
> 不然「边点」是分不清的——断头路和车站都是边，车会不管到底是哪个边点，直接开过去/开到尽头。

`search(g, train, station, expectName, towardNode2, max)` 现在按顺序硬校验，任一条不过就
`Result.fail(原因)`，**绝不换方向重试、绝不拿别的边点当目标**：

| # | 校验 | 失败文案 |
|---|---|---|
| 一 | 站点身份：`station.name` 必须 `equalsIgnoreCase(expectName)`（expectName = 时刻表当前 entry 的目标名） | `目标站名字不符：时刻表=X 站点=Y` |
| 二 | 进入方向：唯一合法驶入边是 `edgeLocation.first → second`（`isPrimary(second)` 为真），该有向边必须真实存在，且 `arrival.node1==a && arrival.node2==b`，站点位置在该边上 | `站点准入侧没有可用驶入轨道：期望 a→b` / `驶入边朝向与准入端不一致` |
| 三 | 沿标定方向单方向展开，**目标判定只认那条 a→b 驶入边**（`k.edge == arrival && k.enter == arrival.node1`） | `搜不到驶入站点的边（上限…扩张…次）` |

规划失败时 `driveTick` **抱闸**（`phaseIdle()` + `holdOutputs()`）并打印 `[drive] 规划失败，抱闸停住：<原因>`——
不许"照旧往前开"。这是"断头路和车站都是边点"那条教训的落地。

`Result.backwards` 改名 `Result.towardNode2`，`describe()` 打印 `方向=朝node2/朝node1`。

**② `TrainDispatcherBlockEntity.ensureDirection()`：实测标定**
- 只观测一件事：给某个面加一点油门后，**车头所在边上 `position` 往哪边变**。
  `position` 变大 ⇒ 朝 `head.edge.node2` 滚（`dirSign=+1`）；变小 ⇒ 朝 `node1` 滚（`dirSign=-1`）。
- 试法：先 LEFT；LEFT 推不动（`CAL_TICK_LIMIT=40` 次决策 = 10 秒，位移仍 < `CAL_MIN_TRAVEL=0.08`）就试 RIGHT；
  **两个都不动 ⇒ `[cal] 两个面都推不动 ⇒ 不驱动（不猜方向）`，冷却 `calCooldown=40` 次决策（10 秒）再试，绝不兜底。试完两面必须 `calFace` 复位成 1。**
- 标定油门 `CAL_THROTTLE=4`；标定期间不规划、不算距站。
- 静止判定**不看 `measuredSpeedMps()`**（读档瞬间它会吐假速度，日志见过 20.61 m/s），
  改看车头在边上位置连续两拍位移 < 0.02。
- 车头跨边 ⇒ 本轮作废重取基线，不拿跨边的数据算方向。
- **换车必须重标**（比较 `train.id`）；标定结果 `DirSign` / `DriveFace` / `CalTrain` 三者随 BE 一起持久化，
  读档不再重标（否则车会在站里乱动）。

**③ `driveTick` 用标定结果**

### 6.2 术语与已确认的点

**「车头跨边」是什么意思**
Create 的 `TravellingPoint` 永远挂在**一条** `TrackEdge` 上，`position` 只在 `[0, 边长]` 内。
车往前开过这条边末端时，点被搬到**下一条**边、`position` 从 0 重新开始。
所以「隔两拍取同一个 position 相减」只在**两拍之间车头还停在同一段轨上**才成立；
一旦跨边，两个 position 属于**不同坐标系**，相减是垃圾（正负都可能颠倒）。
代码里 `[cal] 车头跨边，重取基线` 就是发现 `sameLink` 不成立 ⇒ 丢弃这轮、重新取基线，
**不拿跨边的数字算方向**。正常不该出现（标定油门 `CAL_THROTTLE=4`、窗口 10 秒、阈值 0.08 m）；
真出现说明车本来就在动，或标定油门给大了。

**已确认（用户判断，按此实现）**
- 两个面都推不动：**实际不会出现**。代码里那条 `[cal] 两个面都推不动 ⇒ 不驱动（不猜方向）` 只作安全网保留。
- 静止判定（看车头在边上 position 连续两拍位移 < 0.02）**可以用**。
- 车辆 ID 对比（`train.id` 变了必须重标）**是对的**。

### 6.7 道岔通道打通（2026-11-16 23:37，jar 175,618 字节）

### 13.4 两端导航（1.1.0 定稿，别再改回单端）

**术语（必须用这两个词，不许再说"头/尾"）**

| 词 | 含义 |
|---|---|
| **后端** | route 的 **s 最小** = 搜索起点 = `s=0`。方向参照（`dirSign` / `dirFace`）在它那条边上量 |
| **领先端** | route 的 **s 最大**。**距站/到站只认它** |

车**没有固有头尾**。哪端领先完全由"这次搜索从哪端出发"决定：从后端出发 ⇒ route 的 s 轴就指向行进方向 ⇒ 领先端恒为 s 最大。
换向不需要任何符号翻转，只要换一端重新搜。

**一条路线要同时满足三件事（`RailSearch.validate`，唯一的判定处）**

| 条件 | 阈值 | 不过的后果 |
|---|---|---|
| ① 全部转向架都在这条路线上 | 每根 `sOf` 都有限 | 少一根它就没有 `nextEdgeAfter`，会直行，在道岔上被拉断 |
| ② 没有转向架落在搜索起点后方 | `sMin >= -TAIL_EPS`（0.05 m） | 路线只覆盖车体一半 |
| ③ 车站必须在领先端之外 | `stationS > sMax + LEAD_EPS`（0.02 m） | 就是"背着车站开"，会开过头 |

**这三条对"错误的那一端"必然不成立**（拿领先端当起点，车体就全落在起点后方）⇒ 两端各验一次，合格的那端就是后端。

**三阶段算法（`searchTrainWide`）**

```
阶段一  枚举种子，直到找到一条"覆盖整车"的路线（用来建立 s 轴）
        顺序：上一段用的起点端 → 绑定表顺序；都不行 ⇒ Result.fail，不出发
阶段二  用这条完整路线的 s 轴量出真正的两端 endMin / endMax
阶段三  两端各按①②③验一次（探路结果若起点正是最小端就直接复用，省一次寻路）
        两端都合格（环线）⇒ 优先保持上一段那一端，其次取距站更短的
```

**为什么必须有阶段一（这是 1.0.0 崩在站 3 的根）**：

> 两端是**用 s 轴量出来的**，而 s 轴只能来自某次寻路；某次寻路**未必覆盖整车**。
> 从列车中段的转向架起搜，落在它后面的那些必然算不出 s。
> 拿一条**残缺路线**去定两端 ⇒ 两端都是错的 ⇒ 两条候选全被条件①否掉。

铁证（2026-11-18 日志，站 1/站 2 能过、站 3 崩）：

```
23:29:57 [nav] A端合格：转向架4根全在路线上 s∈[0.00,8.00] 站s=120.2   ← 探路正好从后端起搜
23:30:23 [drive] 规划失败：两端都不合格 ｜ A端/B端：有转向架不在这条路线上  ← 探路从中间起搜
```

**距站只有一条公式**：`d = route.stationS − s(领先端)`。正着开、倒着开都成立。

**相关常量与字段**

| 名字 | 含义 |
|---|---|
| `TAIL_EPS = 0.05` | 条件② 容差 |
| `LEAD_EPS = 0.02` | 条件③ 容差 |
| `Result.distance` | 两端路径里是**领先端距站**；单端 `searchFrom` 路径里仍是 seed 到站的距离 |
| `Result.startPoint` | 这次真正被选作后端的那一点，环线偏好用它做连续 |
| `navTailPos` / `navHeadPos` | 后端 / 领先端的转向架坐标，`refreshNavEnds` 每段规划后重算 |
| `planCooldown` | 规划失败后的退避（10 次决策 ≈ 2.5 s）。一次失败要跑最多 N+2 次寻路，不许每拍重来 |

**`refreshNavEnds` 的两条不变式**
1. 任何一根算不出 s ⇒ 这次串链**整体作废**，保持上一次的两端不动（以前 `continue` 跳过 ⇒ tail 在两根之间乱跳 ⇒ 每跳一次就重标 ⇒ 车"犹豫前后走"）
2. **换端不再作废面标定**（原来那行 `dirSign = 0` 正是抽搐的源头，1.1.0 已删）

### 13.5 方向：`dirFace` + `dirBogey`（1.1.0 定稿）

**旧做法为什么错**：`dirSign` 存的是"路线朝 node1 还是 node2"，那是**边**的属性
（node1/node2 是每条边各自的任意编号），换条边就失效 ⇒ 每次换端都得重标 ⇒
重标期间车不动（`holdOutputs`）⇒ 现象就是"犹豫前后走"。

**现行做法**：标定存两样东西

```
dirFace  = 能把车推动的那个驱动面（1=逆时针 2=顺时针）
dirBogey = 那个面把车推向哪个【物理端】，存那一端的转向架坐标
```

于是任何一次规划只需比一比：

```java
activeFace = navHeadPos.equals(dirBogey) ? dirFace : flipFace(dirFace);
```

换向、换路线、重新规划**全都不用重标**。转向架坐标是物理端，不随路线变。

**标定顺序：必须在规划之后**（没有 route 就没有 s，量不出来）。

```
相位 0  取样：calEdge = 领先端的边；calPos0（边上位置，只用于判静止）；calS0 = route.sOf(领先端)
相位 4  确认静止（同一段边 + 边上位置两拍位移 < 0.02）；跨边就回相位 0
相位 1  给 calFace 加 CAL_THROTTLE=4，量 moved = route.sOf(领先端) − calS0
        |moved| ≥ CAL_MIN_TRAVEL(0.08) ⇒ 标定完成：
          dirFace  = calFace
          dirBogey = (moved > 0) ? navHeadPos : navTailPos
        推不动（CAL_TICK_LIMIT=40 次决策）⇒ 换另一个面；两个都不动 ⇒ 作废 + 冷却 40
```

**静止判定不看测速表**：读档瞬间 `measuredSpeedMps()` 会吐假速度（日志见过 20.61 m/s）。

**硬不变量（每拍检查）**：给着油门时，**领先端的 s 只许增大**。
一旦 `sNow < lastRouteS − 0.02` ⇒ 面选反了 ⇒ `invalidateDirection()`（作废标定）+ `calCooldown=20` + `holdOutputs()`。
这不是"慢一点"的问题，是方向事实错了，**绝不继续推着它开**。

**持久化**：`DirSign` / `DirFace` / `DirBogey`（BlockPos 的 long）三者都写进 NBT；
读档时 `dirBogey == null` ⇒ 把 `dirSign` 也清 0（有面没端 = 半个事实 = 没标定）。

### 13.6 逐转向架道岔（`BogeySteering`）

- **每个绑定转向架是一个独立子系统**，各自算、各自写。少给一根就过不了岔（用户实测："必须每一个转向架都注入红石，否则无法让车辆越过道岔"）。
- 判据照抄 Simurail（§13.2 的符号链），所以**我们算的量和它解读的语义完全一致**，不存在"我算的和它想的不一样"。
- **完全方向无关**：`route.nextEdgeAfter(自己的边)` + `travelDirOf(自己的 TravellingPoint)`。所以车正着开倒着开都对。
- 提前 `ARM_M = 4.0` 米开始给信号；跨过节点后保持 `HOLD_TICKS = 3` 防止在节点上抖动。
- **非 0 值必须每 tick 重写**（3 tick 过期）；0 只在从非 0 退回来时写一次。
- 安全不变量：只允许在 `level.hasChunkAt(pos)` 通过的区块上调 `getBlockEntity`，**绝不触发区块加载**（会重演 C2ME `CompletableFuture.join()` 死锁）。

| 触发 | 位置 |

### 13.11 回归事故：1.1.1 放行 `updateContraptionAnchors` 打断了导航（2026-11-21）

**症状链（必须记死）**

```
1.1.1 把 Carriage.updateContraptionAnchors 从 "HEAD cancel" 改成 "RETURN 放行"
  → Create 按它自己的 TravellingPoint 去摆那节 contraption 实体，
    而那些点是 TrainBinder 直接写的 plot 坐标（两千万量级）
  → 实体被甩远 ⇒ 那一节车厢的区块掉了
  → rosterBogeys() 从 4 根只剩 1 根
  → searchTrainWide 走 pts.size()==1 短路，①②③ 三条硬条件一条都不验
  → 后端 == 领先端、弧长跨度 = 0.00m，却仍然报 ok
  → 车按荒谬路线开出去 ⇒ 出轨
```

**为什么这改动看起来无害**：它只是"取消一个 cancel"。但那个方法是 Create **摆放实体车的入口**，
不是"顺便算个 anchor"。

**正确堵法（1.1.6）**：保留 cancel；另外在 `Carriage.getPositionInDimension` 的 HEAD 里
对我们自己的车返回 `Optional.empty()`。`Train.getPositionInDimension` 是 `findFirst()`，
拿到空就跳过，`BlockPos.containing` 永不被调用，NPE 消失。
**既不放行 anchor 计算，也不需要 `@Accessor` 去写 `positionAnchor`。**

**方法论教训（比 bug 本身更重要）**

1. **出事后算出来的导航数字不能当地形证据。** 车已经跑歪了，`站s / 距站 / 边数` 全是垃圾。
   我曾拿 18:25:04 的 `站s=46.2 / 距站 0.4m` 去推"站 3 的 edgeLocation 摆错了"——纯属推责。
2. **我连着编了两个这样的故事**：`STATION_EDGES` 缓存串方向（该缓存 **0 调用方**，是死代码）、
   站 3 的 `edgeLocation` 摆在缓冲挡上。都是拿事后数据反推的地形侦探小说。
3. **判断"是不是我改坏的"，最有效的手段是版本行为对比**（1.1.0 连跑 8 站全准 vs 1.1.1 之后崩），
   不是对着出事后的日志做侦探。
4. **凡是"取消一个 cancel""放开一个 hook"的改动，一律按高风险处理**，必须单独测一轮再叠别的功能。
5. **`bogeyPoints()` / `rosterBogeys()` 静默缩水是万恶之源**：它让所有下游判据在"更少的信息"上
   仍然声称成功。1.1.5 起有两道守卫：`refreshNavEnds` 的 `bs.size() != roster.size()` 直接 return，
   `driveTick` 规划前的 `resolvedPts != roster.size()` 抱闸拒绝。

### 14.2 根因（2026-11-21 21:05 按字节码重新核实；**上一版是错的，别再引用**）

**错的那一版**：说「旧 `Train` 残留 `SignalEdgeGroup.trains` ⇒ 自己堵自己 ⇒ 排除本车时改比 UUID 就好」。
被用户当场否掉：「难道自己排除了就不堵其他车了？」—— 这句话是对的，那一版的因果链和修法都错。

**对的事实（都可复验）**：

| 事实 | 依据（Create 6.0.10 字节码） |
|---|---|
| `SignalEdgeGroup.trains` / `.reserved` **每 tick 清空重建** | `GlobalRailwayManager.tick(level)` 开头 `for (group) { trains.clear(); reserved = null; }`（只主世界） |
| 每 tick 只有 `movingTrains` + `waitingTrains` 里的车会 `earlyTick` ⇒ 才会往集合里报名 | `GlobalRailwayManager.tickTrains` 只遍历这两个 list |
| `addTrain(t)` = `trains.put(t.id, t); movingTrains.add(t);`（无去重） | 同上 |
| `removeTrain(id)` = `t = trains.remove(id); if (t == null) return; movingTrains.remove(t); waitingTrains.remove(t);` | 同上 |
| `Train` 只 add 不 remove（唯一入口 `addToSignalGroups`） | `Train.earlyTick` |

⇒ **真正的病是「同一个列车 id 存在第二个还在被 tick 的 Train 对象」**：
`addTrain` 用 `put` 覆盖 map 之后，旧对象再没人摘得掉（`removeTrain` 会提前 `return`），
它留在 `movingTrains` 里继续被 tick，继续按它**冻住的 `occupiedSignalBlocks`** 往每 tick 重建的
`SignalEdgeGroup.trains` 里报名 ⇒ **永久占着几段区间，堵住所有人的车**
（虚拟车按引用比较看得见它，物理车经 Simurail 的 `!trains.isEmpty()` 也看得见它）。

**所以「判定时排除本车」根本不是修法**：它只让我们看不见自己的残影，残影照堵别人。
唯一修法：**一个 id 只许有一个对象，多出来的必须从 map + 两个 list 里摘干净**（见 §15）。

**用户确认的另外两条事实**：虚拟车**会**占信号区间；虚拟车**不会**硬拽物理车（没有物理回写）。

### 15.6 1.1.10 实测：车能跑了，但会冲过红灯（1.1.11 修）

**问题 1：侧判定会被信号传播器翻面 ⇒ 凭空"放行"**

### 15.11 1.1.14：黄铜信号机（扳手改成 CROSS_SIGNAL）被整体无视 —— 只读信号区间不够

**用户定义**：黄铜信号机 = 用扳手把信号机改成 `SignalBlock.SignalType.CROSS_SIGNAL`（通过信号机）；
安山那台 = `ENTRY_SIGNAL`（入口信号机）。用户实测现象：
「不是不认黄铜信号机的锁，但是他就是无视了第一个黄铜信号机跨进了闭锁区间」。

**为什么以前看不见它**：以前判红只有两条依据 ——
1. `signal.isForcedRed(node)`（这一侧信号方块被红石上电）
2. `SignalEdgeGroup` 占用（别的车 / 预约）

而通过信号机（CROSS_SIGNAL）的红**两个都不是**：Create 在 `SignalBoundary.tickState` 里
用 `resolveSignalChain(TrackGraph, boolean)` 顺着链子算出来的 —— 它显示的是**前方那台信号机的状态**。
所以：`isForcedRed=false`、本区间也空 ⇒ 我们判 CLEAR ⇒ 车直接跨进后面那一段真正闭锁的区间。

**修法**：`SignalProbe.observe(..., Level)` 增加第三路输入 —— **读信号方块实体上玩家看到的那盏灯**：

```java
for (BlockPos p : 本侧方块.keySet()) {
   if (!level.hasChunkAt(p)) continue;                  // 绝不加载区块（C2ME 会等死服务器线程）
   if (level.getBlockEntity(p) instanceof SignalBlockEntity sbe) {
      if (sbe.getState() == RED) return RED;            // 见到红立即判红
   }
}
```

判红顺序：**灯=RED ⇒ 红** → `isForcedRed` ⇒ 区间占用。日志里现在带
`类型=黄铜/通过(CROSS)` 或 `类型=安山/入口(ENTRY)` 以及 `灯=RED/YELLOW/GREEN/?`，
一眼能看出是哪一台、什么模式、灯是什么颜色。

只认 RED（YELLOW 是"前方被自己预约/接近"的提示色，不该停车）。

### 15.12 1.1.15：被信号锁住时搬动车辆不会重新导航

**现象**（用户实测）：红灯锁存期间把车搬到别处，它不重新寻路，就抱着"旧路线 + 旧锁存"站着。

**为什么**：锁存分支每拍 `return`（只抱闸），**根本走不到"位置不在缓存路线上 ⇒ 重规划"那段**；
而如果搬完之后车还在同一条缓存路线上（`sNow` 仍然是有限值），连那段判定都不会成立。
`driveResult` 一直 `ok`、`driveTarget` 没变 ⇒ `needPlan` 恒为 false ⇒ 永远不重规划。

**修法**：`driveTick` 里加了位置跳变检测 —— 一次决策（5 tick = 0.25 s）最多走
`15 m/s × 0.25 s = 3.75 m`，所以 **|Δs| > 4 m 只能是外力搬动**。命中就：

```java
releaseSigHold("位置跳变");
driveResult = null; driveTarget = null;      // 强制 needPlan
lastRouteS = NaN; calS0 = NaN; calEdge = null;  // 弧长基线/标定基线作废
planCooldown = 0; driveTicks = 0;
holdOutputs(); return;                       // 这一拍抱闸，下一拍重规划
```

日志：`[pos] 位置跳变 s a → b（Δ=…）⇒ 作废路线与信号锁存，重新规划`。

### 15.13 1.1.16：信号机不一定有"红灯"，读的是它自己的状态（RED **和** YELLOW 都算不许过）

用户提示：「信号机可不一定有红灯」「信号机可能都没有灯，只有自己的状态」。
查 `SignalBoundary` 字节码，状态是这么来的：

```java
// tickState(graph)：逐侧（primary = true/false）
if (该侧没有信号方块) continue;
if (group == 对面那个 group) → INVALID;
if (该 group 不存在)        → INVALID;
boolean occupied = isForcedRed(该侧) || edgeGroup.isOccupiedUnless(this);

// resolveSignalChain(graph, primary)

chained = SignalPropagator.collectChainedSignals(...);
全绿/无效 ⇒ GREEN；全红 ⇒ RED；**红绿混合 ⇒ YELLOW**；链上有一台找不到 ⇒ INVALID
```

⇒ **"前方有闭锁区间"完全可能只表现为 YELLOW**（黄铜/通过信号机 = CROSS_SIGNAL）。
只判 `RED` 就等于把通过信号机整台无视 —— 正是用户看到的"无视黄铜信号机跨进闭锁区间"。

**改法（1.1.16）**：

- 不再读方块实体、不碰区块。直接问 `SignalBoundary.getStateFor(pos)` —— 就是 Create 自己
  存在 `cachedStates` 里的那份状态，纯内存。（`getStateFor` 会遍历两侧，用 pos 判断属于哪侧，
  所以传本侧任意一个信号方块坐标即可。）
- **`RED` 和 `YELLOW` 都判为不许过**（INVALID/未知不算红，回落到 `isForcedRed` + 区间占用两路判定）。
- 日志字段改成 `状态=RED/YELLOW/GREEN/?`，并保留 `类型=黄铜/通过(CROSS)` / `安山/入口(ENTRY)`。

**副作用要知道**：YELLOW = 链上红绿混合（岔路场景），保守按"不许过"处理；
如果实测发现某处该放行，再改成"只在我们的分支为红时拦"。

### 15.14 1.1.17：黄灯不是"禁止通行"——黄铜信号机的黄灯就是岔口有路可走

用户纠正：「YELLOW = 链上红绿混合、按保守不许过是何意味？本来黄铜就有岔口放行的功能啊」。
**这条纠正成立**，1.1.16 把 YELLOW 当禁行是过度矫正（会把岔口封死）。

`resolveSignalChain` 的准确语义（字节码）：

| 状态 | 含义 |
|---|---|
| GREEN | 链上全部 GREEN/INVALID（没有一条路是闭的） |
| RED | 链上**全部** RED（每条岔口都闭） |
| YELLOW | 链上**红绿混合** = 这是岔口，**有的路能走** |
| INVALID | 链上有一台信号机找不到 / 本侧没有信号方块 |

⇒ 黄灯的正确处理不是拦，而是**问"我们要走的那条岔口红不红"**。

**1.1.17 做法（全部用 Create 自己的 API，没有自创判据）**：

```java
SignalState state = signal.cachedStates.get(primary);   // tickState 写好的那份，public
if (state == RED)    → 停；                              // 本区间被占 / 红石 / 链上全红
if (state == YELLOW) →
    chained = SignalPropagator.collectChainedSignals(graph, signal, primary);  // public
    只保留"在本段路线上"的那几台（routeHasSignal）
    其中任一台 cachedStates.get(side) == RED ⇒ 停（我们这条岔口闭锁）
    否则 ⇒ 放行，并打一条 [sig] 黄灯放行
```

同时不再读方块实体：`cachedStates` 是纯内存字段，不碰区块（C2ME 安全）。
日志字段：`状态=RED/YELLOW/GREEN/?` + `类型=黄铜/通过(CROSS)`。

### 15.23 1.1.26：轨道外的车，虚拟车凭什么不能"跟着 TP 到场外"

用户问：「这个完全不在轨道上的车，为什么虚拟车没有被 TP 到和它一样的场外或者直接销毁？」

**三条事实**：

1. **Create 的 `Train` 只能活在轨道边上**：每节车厢就是一个 `TravellingPoint(edge, position)`，
   `position` 是沿边的弧长。**世界上不存在"轨道外的列车坐标"**，所以"TP 到场外"根本不可表示 ——
   这也是为什么 `TrainBinder.bind` 在结构不在轨道上时只能直接失败（`物理结构不在轨道上（或跨图）`）。
2. **Create 只自动销毁 `invalid=true` 的车**（`tickTrains` 里 `if (train.invalid) 移除`）。
   而 `derailed=true` 的车它会一直留着 —— 我们的日志正是 `invalid=false derailed=true`，
   所以它既不走、也不消失，就那么占着一段区间。
3. 于是唯一正确的做法是**我们自己判定并注销**。

**1.1.26 实现**：新增 `physicalOnTrack()`（任取一根绑定转向架，看它的轴有没有边），
在 `syncTrainPresence()`（每 20 tick）里：

```java
if (boundTrain != null && !physicalOnTrack() && ++offTrackTicks >= 2) {
   dissolve();            // 注销虚拟车（map + movingTrains + waitingTrains 全摘）
   presenceRetry = 40;    // bind 也会失败，别立刻重建
}
```

连续两次（约 2 秒）才动手，避免跨边那一拍抖动把车误注销；回到轨道上时 bind 会自动重建。
日志：`[presence] 物理结构不在轨道上（连续 2 次）⇒ 注销虚拟列车 xxx`。

### 15.27 架构决定（1.1.29）：不追"速度绝对相等"，改"位置快照"

用户提出根本问题：「你怎么确保虚拟车的速度和物理车绝对相等？**快了要锁物理车，慢了要锁后头车**」。

**这个目标本身不可达，也不该追**：

- 虚拟速度是**推导量**（从物理位移反算），物理速度是**观测结果**；两者之间永远有采样误差、方向符号、
  拐点、加减速相位差。任何"跟在后面的积分"都会累积或滞后。
- 误差有两个方向，两个方向都是灾难：**超前 ⇒ 虚拟车提前占住前方区间 ⇒ 锁住物理车自己**；
  **滞后 ⇒ 该占的区间提前释放 ⇒ 后车看到绿灯撞进来**。
- 所以这不是调参问题，是模型错了。

**现在的实现是三写者打架**（这就是系统性问题的根源）：

| 写者 | 干什么 |
|---|---|
| `TrainSpeedInjectMixin`（tick HEAD） | 把 `physicalSpeedPerTick()` 写进 `train.speed` ⇒ Create 用速度**积分**车厢位置 |
| `TrainBinder.reanchor`（我们每 tick） | 直接把物理转向架的 edge+position 抄给车厢 |
| `TrainFreezeMixin`（tick TAIL） | 再把 speed 置 0 |

三者对同一份位置的三个来源、三个时序 —— `spacing=2`、`[crash]` 每 tick 触发、占区错乱全是它的下游。

**新模型（1.1.29 起逐步落地）：虚拟车是"快照"，不是"积分出来的车"**

```
虚拟车速度恒为 0            ⇒ Create 的积分不参与任何位置计算
位置每 tick 由物理车直接写入 ⇒ 误差恒为 0，且不累积
占区在写入之后立刻重算      ⇒ 区间 = 物理车此刻真正覆盖的区间
```

于是"速度相等"这个问题**消失**：没有积分就没有漂移，±0 是构造出来的，不是调出来的。

**1.1.29 已做**：`TrainSpeedInjectMixin` 不再注入物理速度，`speed` 恒置 0（`manualTick = true`）。

**还没做（下一步，必须做）**：**两阶段 tick**。
现在每辆车的"快照"和"决策"交错执行：A 快照 → A 判断信号 → B 快照 → B 判断信号。
B 判信号时看到的 A 可能是上一拍的位置（差 ≤1 tick）。做法是在 `DispatcherTicker` 里拆成两遍：

```
第一遍：所有调度器 snapshot()   —— 写位置 + 重算占区
第二遍：所有调度器 decisionTick() —— 判信号、出油门/制动
```

这样"所有人看到的占区都是同一拍快照"，残余误差只有 1 tick 内的执行延迟，且**不累积**。

### 15.28 1.1.30：快照模型落地（reanchor 重写 + 单一写者 + 两阶段 tick）

**这一版是"减法"**：删掉一个写者、删掉一条路线投影、删掉一次每 tick 一万多次方块扫描。

#### 一、先查清"位置到底由谁决定"（读 Create 6.0.10 字节码得到，别再猜）

`Train.collectInitiallyOccupiedSignalBlocks()` 起手取 **最后一节车的 `getTrailingPoint()`**，
然后调 `Train.forEachTravellingPointBackwards(biConsumer)`。这个方法体的实际顺序是：

```
for (int i = carriages.size() - 1; i >= 0; i--) {          // 车尾 → 车头
    Carriage c = carriages.get(i);
    CarriageBogey tb = c.trailingBogey();
    accept(tb.trailing(), dist);                            // 先"后轴"
    accept(tb.leading(),  tb.type.getWheelPointSpacing());   // 再"前轴"
    if (!c.isOnTwoBogeys()) continue;
    CarriageBogey lb = c.leadingBogey();
    accept(lb.trailing(), c.bogeySpacing - total - lbWS/2);
    accept(lb.leading(),  lbWS);
}
```

而 consumer 是
`point.travel(graph, dist, point.follow(nextPoint), listener, point.ignoreTurns())`。

**两条结论，改变了整个设计：**

1. **位置完全由这些 `TravellingPoint` 决定，`train.speed` 根本不参与。**
   所以"虚拟车速度必须和物理车绝对相等"这个要求不需要满足 —— 没有积分就没有漂移。
2. **`distance` 是"从当前点沿轨再走多远到下一个点"**，方向由点的先后顺序隐式给出。
   也就是说：**点的顺序错了 20 m，占区就占到别处那 20 m 上，本车该占的那段反而空着**
   ⇒ 后车开进来。顺序是**安全相关**的，不能靠世界主轴排序糊过去。

`Carriage.getLeadingPoint() = bogeys.getFirst().leading() = points.getFirst()`；
`getTrailingPoint() = bogeys.getSecond().trailing() = points.getSecond()`
（`CarriageBogey.points` 是包私有，只能通过 public 的 `leading()/trailing()` 写）。
所以**每节车有 4 个点**要写：两个转向架 × 各自 2 根轴。

#### 二、旧 `reanchor` 错在哪（1.1.26 日志实证）

走的是 `CreateRouteBinding.fromPoints(anchor, [tail])` → `boundedPointAt(sLead/sTail)`。三个后果：

1. **一个点都没写**：路线一失效就抛 `RouteInvalidException`，整次调用在写点之前就跳出。
   1.1.26 日志里 `[anchor] ... route must be rebound` 出现 **136 次**，而车厢位置一次都没更新。
   这也解释了为什么 1.1.29 "只把速度摘掉"会让车彻底不动 —— 位移从来没走过这条路。
2. **所有车厢被塞进同一对 sLead/sTail**，两节车叠在同一个位置。
3. 每 tick 扫 25×17×25 = 10625 个 `getBlockEntity`（外加 C2ME 风险）。

#### 三、1.1.30 的做法

- **`TrainBinder.STRUCTURE`**：`bind` 时把"每节车 → 它的物理转向架方块坐标（前→后）"记死。
  存 `BlockPos` 不存 `BlockEntity` 引用（会被卸载），取不到就**整次不写**并写进 `anchorProbe`。
  世界重载后由 `adoptStructure()` 重新登记；登记不出来（或节数与车上车厢数不符）就重建车。
- **`reanchor` = 纯快照**：逐节车、逐转向架，把 `getAxle(true)/getAxle(false).getTrackPoint()`
  的 `edge/node1/node2/position` 直接抄进 `bogey.leading()/bogey.trailing()`。
  无路线、无投影、O(转向架数)。失败策略是"宁可不写，绝不写半列"。
- **哪根轴在前**：由几何定 —— 两根轴在"行进方向"上的投影谁大谁在前。
  行进方向取**最前面两根转向架中心的连线**（相邻、一定非零、弯道也可靠），
  比去猜 Simurail 的 `reverseStates` 稳。
- **`chainOrder()`：世界主轴排序 ≠ 沿轨顺序**。`rosterBogeys()` 是 `BogeyRoster.ordered()`
  （按世界主轴），在 S 弯/斜线上不代表列车前后。所以 `bind` 先用最近邻把转向架串成一条链
  （O(n²)，n≤10，只在建车时跑），再按子结构分组。
  这样"车厢顺序"和"车厢内转向架顺序"都是物理前后序，方向一致。
  量不出中心就保持原序，**不做推测性连接**。
- **`bogeySpacing` / `carriageSpacing` 的语义**（对字节码核过）：
  - `Carriage.bogeySpacing` = 这节车**前后两个转向架中心**之间的距离（不是同一根转向架两轴！1.1.28 前量错了 ⇒ 2 m）；
  - `Train.carriageSpacing[i]` = 第 i 节后转向架中心 ↔ 第 i+1 节前转向架中心。
  两者现在都用 `bogeyCenter()`（两根轴世界位置中点）量。
- **单一写者**：`Carriage.travel` 被 `CarriageAnchorMixin.hexie$blockCarriageTravel` 整个拦掉，
  返回 0。原因：`Train.tick` 即使 `speed == 0`，也会给第 2 节车起喂一段"耦合余量"
  `bogeySpacing - getAnchorDiff()` —— 我们没有 contraption 实体，`getAnchorDiff()` 取不到东西，
  余量就等于整节车长（十几米），Create 会沿轨**真的把点挪十几米**，还在道岔上用 `follow()` 自己挑边。
  拦掉之后位置 100% 由物理轴快照决定。
- **速度写者合并成一个**：`TrainFreezeMixin` 删除（文件 + mixins.json 都去掉了），
  TAIL 归零合并进 `TrainSpeedInjectMixin.hexie$afterTick`。HEAD 清 destination + `speed=0`，
  TAIL 再压一次（tick 中途 `Navigation.tick` / `ScheduleRuntime.tick` 会写非 0）。
- **撞车检测一起拦**：`Train.tick → collideWithOtherTrains` 对我们自己的车直接取消。
  两辆虚拟车的端点都是从物理轴抄的，物理上本来就挨着，Create 拿它们当两辆独立车比间距必然判撞。
  再往下就是 `Train.crash`（1.1.26 实测 **1588 次**）。**但诊断价值留住**：
  每辆车前 3 次 + 之后每 200 次仍打一行 `[crash] 跳过 Create 的撞车检测`。
- **两阶段 tick**（`DispatcherTicker`）：第一遍全体 `snapshotPhysical()`（只写点、不决策），
  第二遍全体 `serverTick()`。跨车判断不再差一 tick（20 m/s 时 1 m）。
  `serverTick` 内部原有的 reanchor 调用保留 —— 重复抄同一批点是纯拷贝，幂等。
- **`TrainStateReader`**：速度不再读 `train.speed`（恒 0，会把"在跑"谎报成"停了"），
  改读 `TrainBinder.motionOf(trainId).speed()` —— 唯一真实来源，由物理转向架中心逐 tick 位移算出，
  **每车独立**（旧代码用的全局 `prevAnchorS/lastAnchorS` 在多车下会互相污染，已删）。

#### 四、删掉的东西（防止后人再修回路线投影）

`TrainBinder` 里的 `lastAnchorS / prevAnchorS / lastRoute / lastGraph / setPoint / syncPoint /
copyInto / CreateRouteBinding` 引用 **全部删除**。
如果哪天有人想"用路线把车厢点算出来"，先读 §15.28 第一节。


1. `[bind] 结构` 一行必须出现：**车厢数、总转向架数、每节几根、每节间距**。

```
[anchor] 0 次                                    ← 旧版 136 次异常、一个点不写
```

也就是说第二种在语义上根本不算占用。1.1.26 之所以"无视了第一个黄铜信号机"，

**1.1.31 只加诊断，不改判定**（红灯照样停，不兜底）：

- 新类 `TrainCensus`（**纯只读，只拼字符串，不写任何状态**）：
  - `group(groupId, self)`：把 `SignalEdgeGroup.trains` 原样打出，逐车标

  1. `bindTrainNow` 成功 → `[sig][全部车]`（**不用等信号**，建车就有）；
  2. 压速分支 `前方红信号 ⇒ 限速` → `[sig][是谁]`；
  3. 锁存超时 240 拍 → `[sig][是谁]` + `[sig][全部车]`（强制松开前）。

**下一步看日志怎么判：**

- `全部车 = 1 辆` 且 `[sig][自占]` ⇒ 是自锁（情况 B）。
  那时的修法**不是**"红灯可以放行"，而是把 RED 解析成"被谁占"：

### 15.31 1.1.33：两个"假警报"—— 轨道末端 + 停得太远

**1.1.32 实机：信号自锁已解决，车正常跑。剩两处观感问题，根因都在我们自己。**

#### 一、"一节车厢已到达轨道末端"是假的

那句话是 Create 的 `create.train.status.end_of_track`。来源（`Train.tick` 字节码）：

```
boolean anyBlocked = false;                       // 630: iconst_0 / 631: istore 15
for (Carriage c : carriages)
    anyBlocked |= c.blocked || c.isOnIncompatibleTrack();   // 926~950
...
if (anyBlocked) {                                 // 1056
    speed = 0;
    navigation.cancelNavigation();
    runtime.tick(level);
    status.endOfTrack();                          // ← 屏幕上那句
}
```

`c.blocked` 由 `Carriage.travel` 设置，而它已经被
`CarriageAnchorMixin.hexie$blockCarriageTravel` 整个拦掉了 ⇒ 唯一来源是
`isOnIncompatibleTrack()`：

```
AbstractBogeyBlock.isOnIncompatibleTrack(carriage, leading):
    return edge.getTrackMaterial().trackType != this.getTrackType(bogey.getStyle());
```

也就是说它拿"虚拟车端点所在轨道边的材质类型"去比"我们在 `bind` 里**编**给它的那根
`AllBlocks.SMALL_BOGEY` + `STANDARD` 风格所期望的类型"。
**那根转向架标签本来就是为了让 Create 的数据结构能成型而虚构的**
（真实转向架是 Simurail 的物理转向架），它不该反过来判物理车能不能走。

⇒ 1.1.33 在 `Carriage.isOnIncompatibleTrack` 的 **RETURN** 处拦：只有 Create 真判成
`true` 时才改成 `false`，并打一行 `[track]` 把**实际材质 id** 和期望的 `standard` 写出来
（每种材质只报一次）。不用 HEAD，是因为 HEAD 无条件返回 false 会在标准轨道上也白喊一句。

**这一条同时解释了为什么"1.1.30 之前没有"**：那时候虚拟车的点是冻死的，永远停在那一条边上，
碰不到别的材质；现在点跟着物理轴走，才会撞上材质不同的轨道边。

#### 二、停车点离信号机太远

```java
// 旧：一锁存就全力抱闸
this.drivePhase = PH_BRAKE; this.brakeCmd = 15;
```

而锁存触发点是 `dSig <= brakeDist + 6.0`（`+6` 是吃掉决策节拍/执行延迟的余量）。
**余量被当成了停车位置** ⇒ 实测在离信号机 **6.2 m** 处就停死
（`[sig] 前方信号 距离=6.2 刹车需要=0.5 ⇒ 锁存`）。

现在：锁存触发点不动（早一点决定停是好事），但**停车位置**改成信号机前 0.5 m 的刹车曲线：

```
dSig   = sigHold.s - sNow
vAllow = sqrt(2 * 0.5 * max(0, dSig - 0.5))     // 用保守减速度 0.5，宁可早刹
if (v <= 0.05 || dSig <= 0.5 || v > vAllow) ⇒ PH_BRAKE / brake=15
else                                        ⇒ PH_COAST / brake=0
```

用 0.5 而不是 `A_BRAKE=0.6`：实测减速度 0.53~0.67，取下界才不会因为算得太乐观而冲过信号机。
另外每次真正停稳会打一行
`[sig] 已在信号机前 X m 停稳（目标是 0.5 m）` —— 这是"离信号机多远停住"的唯一实测依据。

**进游戏要看：**

1. 那句"一节车厢已到达轨道末端"不再出现；
2. 若出现 `[track]` 日志 → 记下它报的材质 id（说明轨道用了非标准材质，忽略是安全的，但要记账）；
3. `[sig] 已在信号机前 X m 停稳` 里的 X 应该 ≈0.5~1.5；若仍偏大或冲过，就是曲线参数问题，按这条日志调。

### 15.32 用户环境事实：轨道一直是非标准材质（1.1.34）

用户确认：**"我一直都用着非标准材质"**。这条要记死，不要再当异常。

```
3: areturn
```

⇒ `Train.tick` 的 `anyBlocked` 每拍为真 ⇒ `speed = 0` + `navigation.cancelNavigation()`
+ `status.endOfTrack()` ⇒ 屏幕上那句"一节车厢已到达轨道末端"。

#### 顺带核实：虚构的转向架**另一个**参数正好是对的（差点漏掉）

担心的是同一批虚构标签里的 `getWheelPointSpacing()` —— 它被

查了：`StandardBogeyBlock.getWheelPointSpacing()` 是**常量 2.0**：

```
0: ldc2_w 2.0d
3: dreturn
```

而物理转向架实测两根轴间距 = **2.00 m**（1.1.26 日志里的 `spacing=2` 就是这个量）。
**巧合但正确**，所以占区长度没有被这个虚构参数带歪。改转向架块类型（比如换成窄轨的）
反而会把这个数改坏 —— 所以**不要为了"消掉不兼容"去换 bogey 块**，
用 mixin 把 `isOnIncompatibleTrack` 拦掉才是对的：虚构标签不该判物理车。

#### `getTrackType` 的另一处用途：不影响我们

`AbstractBogeyBlock.getValidPathfindingTypes(style)` = `ImmutableSet.of(getTrackType(style))`，
只被 Create 自己的寻路用来避开"转向架走不了的轨道"。我们的导航是
`RailSearch`（自己写的），并且每拍把 `navigation.destination` 清成 null，
Create 的寻路根本不跑 ⇒ 与我们无关。

### 16.4 【事故】手操状态下虚拟车不跟实体车（1.2.0 修）

**用户报告**：「现在是玩家操控状态，出事了，虚拟车不跟着实体车跑了」

**根因：位置镜像被 `manualMode` 挡住，有两道门，同时生效。**

```java
// 门①：DispatcherTicker 阶段 1 的入口
public void snapshotPhysical() {
   if (this.level == null || this.level.isClientSide || this.manualMode) return;   // ← 手操直接不镜像

// 门②：serverTick 里那段
if (!this.manualMode && this.level instanceof ServerLevel slTP) {
   TrainBinder.reanchor(trA, slTP, this.worldPosition);     // ← 也被 !manualMode 包着
   ... 占区同步 ...
}
// 而 serverTick 的手操分支在 reanchor 之前就 return 了
```

⇒ 手操时**一处都不写**，虚拟车的点冻在最后一次自动模式的位置上，占区也跟着冻 ⇒
它不再代表物理车，别人看它那段永远是错的。

**为什么以前"看起来能用"**：1.1.30 之前 `Carriage.travel` 还没被拦，
老手动分支里那三行 `train.manualTick/targetSpeed/approachTargetSpeed(...)` 让
**Create 自己的 Navigation 去开虚拟车** —— 手操时虚拟车是靠 Create 的积分跟上的，不是靠 reanchor。
1.1.30 拦掉 `travel` 之后这条路就断了，于是**手操模式从 1.1.30 起其实一直是坏的**，
只是没人测；1.2.0 我又把那三行死代码删了，等于把"看起来还能动"的最后一点痕迹也去掉了。

**修法（原则：位置镜像与"谁在开车"无关）**

1. `snapshotPhysical()` 去掉 `|| this.manualMode` —— 阶段 1 对所有模式一律镜像。
2. 占区同步从 `serverTick` 搬出来，抽成 `syncOccupancy(Train)`，在 `snapshotPhysical` 里紧跟
   `reanchor` 之后调用 —— 于是手操时位置和占区都继续更新。
3. `serverTick` 里那段被 `!manualMode` 包着的重复逻辑**整体删除**（只留一套实现）。

**教训（写进铁律候选）**：
凡是"每拍必须发生的镜像/同步"，**不许**按控制模式加门；控制模式只该决定
"给不给油门/刹车"，不该决定"要不要把物理事实抄过来"。

### 16.5 【缺口】无视没有虚拟车的物理车（1.2.0 修）

**用户报告**：「他似乎会无视没有虚拟车的物理车，虽然物理车在没有绑定虚拟车的情况下可以在信号上占用区间，但我们的车直接无视」

**根因：占区有两套，我们只查了一套。**

```
SignalEdgeGroup.trains  = Create 的 Train 对象（我们的虚拟车、别人的 Create 车）
SignalEdgeGroup.bogeys  = Simurail 加的 @Unique Set<PhysicsBogeyBlockEntity>（物理转向架）
                          ← 没有绑定虚拟车的物理车【只在这里】
```

`SignalEdgeGroupMixin`（Simurail，字节码核过）：

```java
@Unique private Set<PhysicsBogeyBlockEntity> bogeys = new HashSet<>();

@WrapMethod(method = "isThisOccupiedUnless(Lcom/.../Train;)Z")
private boolean simurail$modifyIsOccupied(Train train, Operation<Boolean> original) {
    return !bogeys.isEmpty() || original.call(train);
}
```

而 `SignalProbe.occupancy()` 只 stream 了 `group.trains` ⇒ **物理车对我们完全隐形**，直接开过去。

**为什么不用 Simurail 现成的 API（两个都不能用，都核过源码）**

| API | 实现 | 为什么不能用 |
|---|---|---|
| `simurail$isOccupiedUnless(PhysicsBogeyGroup)` | `group.bogeys.stream().noneMatch(bogeys::contains) && !bogeys.isEmpty() \|\| ...` | `noneMatch` 要求"我方**一根都不在**该区间"才判占用 ⇒ **我方一根 + 对方一根混在同一区间时返回 false**，恰是最该拦的场景漏判 |
| `simurail$isThisOccupiedUnless(PhysicsBogeyBlockEntity)` | `bogeys.size() > 1 \|\| (!bogeys.contains(bogey) && !bogeys.isEmpty()) \|\| ...` | 写死 `size() > 1` ⇒ **我方两根转向架同处一个区间就判"被占"** ⇒ 自锁（我们 16.7 m 的车很容易跨两根） |

⇒ 只能**直接读那个集合**，再用"这个 BlockPos 是不是我们自己车的转向架"（`TrainBinder.isOurBogey`，从 `STRUCTURE` 查）精确排除自己。

**实现**：新类 `PhysicalOccupancy`（反射 `SignalEdgeGroup.bogeys`；`@Unique` 字段可能被 Mixin 改名，
所以先试名字、再按"泛型里带 PhysicsBogeyBlockEntity 的 Set 字段"扫；失败**大声报一次**，不假装没人占）。
`SignalProbe.occupancy()` 加第三个条件 `otherPhysical`。

**诊断**：`[sig][是谁]` 和 `[sig]` 的 BLOCKED 原因里都加了
`物理转向架=N(含别人的)` / `(全是我们的)` —— 这条能直接看出反射有没有生效。

**待验**：放一辆**没有调度器**的物理车停在我们要进的区间里，我们的车必须停。
若日志里 `物理转向架=?（反射失败）` 说明字段名/结构变了，`[sig][物理占区]` 会有一行 WARN。

### 16.6 列车命名（1.2.0 新增）

**用户要求**：「不管是虚拟车还是物理车都应该有一个名字，而不是显示一个未命名列车，我们能不能通过铭牌给虚拟车注入这个名字呢？」

**可行性（都核过字节码/源码）**

| 端 | 字段 | 持久化 |
|---|---|---|
| 虚拟车 | `Train.name` 是 **`public Component name`**（Create 6.0.10），界面读它，为 null 才显示 `create.train.unnamed`「未命名列车」 | `Train.write` 写 `"Name"`、`Train.read` 读回 ⇒ **会落盘** |
| 物理车 | `PhysicsBogeyBlockEntity implements Nameable`：`setCustomName/getCustomName`；`PhysicsBogeyGroup.displayName` 取自**链上第一根**转向架的 `getDisplayName()` | NBT `custom_name` ⇒ **会落盘** |

**交互：铭牌右键调度器**（用铁砧改过名的任意物品）

- 名字来自原版 `DataComponents.CUSTOM_NAME`，**零新增包、零新增 UI**。
- 走 NeoForge 的 `PlayerInteractEvent.RightClickBlock`，**不重写 `useItemOn`** ——
  1.21.1 里那个方法声明在 `net.minecraft.world.level.block.Block` 上，
  第一版加 `@Override` 直接编译不过（"不能覆盖"），而且签名一偏就会**静默失效**。事件不依赖签名。
- 有主且非归属者 ⇒ 拒绝并提示；否则 `be.setTrainName(name)` + 提示 + 拦掉这次右键（不再顺手开界面）。

**两端注入**（`TrainDispatcherBlockEntity.setTrainName / applyTrainName`）

1. `Train.name = Component.literal(name)`；
2. 每根绑定转向架 `setCustomName(...)` + `setChanged()` + `sendData()`。

**名字由调度器自己存一份**（BE 的 NBT `"TrainName"`），因为虚拟车重建是**新对象**、`name` 会丢；
`read()` 里（仅服务端）和 `bindTrainNow()` 成功之后都会重新 `applyTrainName()`。

**进游戏要验**
1. 铁砧上把任意物品改名 → 右键调度器 ⇒ 快捷栏提示「已把这列车命名为：…」；
2. Create 的站台/列车界面里那辆车**不再显示「未命名列车」**；
3. 物理转向架的界面/编组名也变成它；
4. 重启世界 + 解绑重绑之后名字还在。

### 16.8 名字为什么"改了没用"：Train 根本不同步（1.2.0）

**用户反馈**：铭牌改名 111，日志已经打出 `[name] 虚拟车名字 ← 物理结构铭牌「111」`，
但**用 Xaero 小地图看，实体名还是「未命名列车」**。

**两个被证实的事实**

1. `train.unnamed` **不是显示兜底，是构造函数默认值**：
   ```java
   public Train(…, boolean, int) {
       this(…, CreateLang.translateDirect("train.unnamed"), TrainIconType.getDefault(), …);
   }
   ```
   所以 `Train.name` 永远非 null，新建的虚拟车一出生就叫"未命名列车"。

2. **`Train` 一个 send/sync 方法都没有**（全类核过：只有 `updateSignalBlocks`/`updateConductors`/
   `shouldCarriageSyncThisTick` 之类，没有 packet/send/sync）。它是**纯服务端对象**。
   客户端要知道名字只有两条路：
   - `TrainEditPacket` / `TrainEditPacket$TrainEditReturnPacket`（`AllPackets.S_CONFIGURE_TRAIN`）——
     **但我们核了 `TrainEditReturnPacket.handle(LocalPlayer)` 只是 `handleSided(null)`，
     去更新某个 GUI 的局面，不会写回客户端 `Train`** ⇒ 走它等于白发；
   - `TrainMapSync` / `TrainMapSyncPacket`（只服务地图）。

**实体名从哪来**：`CarriageContraptionEntity.getDisplayName()`（字节码）：
```java
if (carriage == null) return CreateLang.translateDirect("train");   // 「列车」
return … carriage.train.name …
```
Xaero 这类按实体名显示的地方拿到的就是**客户端那个 `Train`** —— 它永远停在默认名。

**做法（不新增网络包）**

1. `TrainDispatcherBlockEntity.write/read` 的 {@code clientPacket} 分支带上 `"HexieTrainName"`；
   名字变化时 `sendData()`。
2. 客户端 `read(clientPacket=true)` ⇒ `TrainBinder.putClientName(boundTrain, name)`（静态缓存）。
3. 新 mixin `CarriageNameMixin`：`CarriageContraptionEntity.getDisplayName()` 的 RETURN 处，
   用 `trainId` 查缓存，有就返回我们的名字（`TrainBinder.clientNameOf`）。

**教训**：改一个字段之前先确认**它是不是同一个对象**。`Train` 是服务端对象，
客户端那份是另一条独立构造出来的，界面上看到的往往是后者。

### 16.9 【我的 bug】名字只生效一次：比的是"名字变没变"，不是"哪台车"

**用户截图**：故意让它寻不到路，弹出的 `TrainStatus` 播报
```
关于列车的信息：未命名列车
  找不到前往下一个目的地合适路线
```

**这条播报读的是服务端 `Train.name`**（`train.status` = "关于列车的信息：%1$s"）——
所以它说明那台车的 `name` 确实还是默认值，不是我上一版以为的"客户端副本"问题
（客户端副本问题是真的，但那是另一个症状：Xaero 那边）。

**根因（我自己写错的）**

```java
if (java.util.Objects.equals(name, this.lastTrainName)) return;   // ← 只比名字
```

虚拟车重建时是**一个新的 `Train` 对象**，名字回到构造默认的「未命名列车」，
而 `lastTrainName` 仍等于铭牌名 ⇒ 判成"没变" ⇒ **永远不重注入**。
日志里 `[name]` 只出现 **1 次**，正好印证（如果重注入过，重建后还会再打一次）。

**修法**：判据改成**对象身份**

```java
private Train lastNamedTrain = null;   // 上次注入到哪台车对象上
if (train != null && train == lastNamedTrain && Objects.equals(name, lastTrainName)) return;
```

对象换了就重注入。清除名字时**回落到 `Component.translatable("create.train.unnamed")`
而不是 null** —— `TrainStatus` 直接把它当参数用，null 会显示成 "null"。

**教训（第二次同类错误）**：判断"要不要重新做"时，凡是**对象可能被重建**的场合，
判据必须是**对象身份 + 参数**，不能只看参数。虚拟车重建、TravellingPoint 重建、
CarriageBogey 重建都是同一个坑。

### 18.1 先把"环境到底是什么"钉死（不是猜，是逐日日志核出来的）

`2026-11-22-6/-7` 两份是 0.1.4，其余全是 0.1.0。

**0.1.3 与 0.1.4 在转向上一模一样**：`git log origin/main` 里 0.1.4 的发布提交

「Add support for Loconautics schedule initiated decoupling」。
所以"1.3"和"1.4"是同一套转向代码 —— 用户说的"1.3 环境"= 新 Simurail。

### 18.2 0.1.0 与 0.1.3 的转向判据是**两套东西**（唯一相关改动）

```
commit 2cb847b  2026-09-26  Change turn control to be based on track curvature
commit bdf67f8  2026-11-14  Fix inverted condition in bogie steering（修 straightTarget 条件写反 + 补 bestTarget==null）
```

**0.1.0（连续式）**：`wish = 行进方向 + steerValue × trackAxleFrame.lateral`，
再和每条候选边的弦（`pos(1)-pos(0)`）求点积取最大。steer 是"往哪边掰一点"。

**0.1.3/0.1.4（离散式）**，`PhysicsBogeyAxle.steer()` 源码 1032 行起：

```java
Vector3dc trackLat = trackFrame.lateral;
turn = SimurailMath.cachedControlPoints(edge.getTurn()).curvature(0, turnCurvature).dot(trackLat);
!edge.isTurn()            → straightTarget
|turn| < EPSILON(1e-6)    → straightTarget
turn < 0                  → leftTargets
turn > 0                  → rightTargets

steerValue = bogey.getGroupSteerValue();
straightTarget != null && (steerValue == 0
    || steerValue < 0 && leftTargets.isEmpty()
    || steerValue > 0 && rightTargets.isEmpty())  → 直行
!leftTargets.isEmpty() && steerValue <= 0          → 左组
否则                                                → 右组
```

⇒ **0 与 ±1 是三件不同的事，中间值毫无意义**；左右完全由 `trackFrame.lateral` 的符号定。

### 18.3 我们自己写错在哪（两条）

1. **自己在世界系里反推横向**：旧代码 `right = travel × (0,1,0)`。
   而他们的 `trackFrame.lateral` 是**用 `trackAxleFrame.direction` 翻正过**的
   （源码 413-419 行，`dot < 0` 就 `direction.negate(); lateral.negate();`）。
   自己拼的向量和他们那条**不保证同向** ⇒ 一旦反了就是"该进岔走直、该直行走岔"。
   **修法**：判据整行照抄他们的 —— `curvature(0) · axle.getTrackFrame().lateral()`，
   同一行代码同一个向量，从此不存在符号分歧。

2. **"到岔口前 4 米才上值"的竞态**：旧代码 `ARM_M = 4.0` + `remainingToLegEnd` 门槛。
   物理车很快，晚一拍就是整列车走错股道；而遥控值只活 3 tick（`getRemoteSteerValue`
   里 `currentTime - left > 2` 就 `i.remove()`），窗口本来就窄。
   **修法**：去掉 4 米门槛，**整条腿都挂着**。安全性论证：值只在节点被读，
   而路线里凡是出现多个候选边的节点必然就是某条腿的终点 = 我们本来就要决定的岔口；
   非岔口的节点只有一个候选，挂不挂都一样。

### 18.4 顺手加的现场取证（这是下次定位的关键）

`write()` 写完遥控值后**立刻读回 `bogey.getGroupSteerValue()`**：

```
[steer] (x,y,z) 打【行进右】 目标边=弯 3.21m 读到=1.0     ← 正常
[steer] (x,y,z) 写了遥控=-1 但转向架读到=0.0 —— Simurail 里本地红石非 0 就直接
```

## 19. 和谐轨道上的"迟疑不前"到底是不是外轨超高（1.2.2）

**用户原话**：「它在和谐的轨道（有外轨超高机制）上表现出迟疑不前的特征，我怀疑是外轨超高导致我们判定车不在轨道上面导致的」。

### 19.1 先回答：外轨超高**不在**我们的判据上（有代码证据）

我们的"在不在轨道上"只有三处，全部只看一件事 —— **PhysicsBogeyAxle.getTrackPoint().edge != null**：

 + "`" + 
physicalOnTrack()      TrainDispatcherBlockEntity  任一绑定转向架的 leading 轴有 edge ⇒ 算在轨道上
hasTrackPoint(b)       TrainBinder                 两根轴都有 edge 才算可用
TrainBinder.bind       物理结构不在轨道上（或跨图）   group.getTrackGraph() == null 时兜底找图也失败
 + "`" + 

这些 edge 由 Simurail 的 PhysicsBogeyAxle 决定，找轨入口是
TrackSegmentHelper.findBlockTrackSegment，它只读 Create 的 ITrackBlock：

 + "`" + 
getNearestTrackAxis / getUpNormal / getElevationAtCenter / getMaterial
TrackTypeOverrides.getTrackType(material) → 轨型过滤
TrackSegment.inLineRange:  vCos >= 0.5, 竖直 vDist ∈ [-1.5, 0.375](不反向), 横向 lDist ∈ [-0.5, 0.5]
 + "`" + 

**和谐的超高完全进不到这条路上**：

| 超高相关 | 位置 | 谁在用 |
|---|---|---|
| cantRadians | TrackGeometry.Sample | 和谐自己的车体姿态 |
| ollRadians / AttitudePolicy.FOLLOW_TRACK | VehiclePose | 和谐自己的车厢 |
| TrackRailSurface（PIVOT=0.125, HALF_GAUGE=0.7546875, otatedSection, esidual） | compat/create | CreateRouteBinding\.sample() |
| SimurailBogeySuspensionPose | client/render/bogey | **纯渲染**（转向架悬挂外观） |

而 StandardTrackBlock（extends Create 的 TrackBlock）**只覆盖了**
useItemOn / prepareTrackOverlay / prepareAssemblyOverlay / getShape / getInteractionShape /
getCollisionShape / getBogeyAnchor，**没有覆盖 getUpNormal、getElevationAtCenter**。
⇒ 超高既不改 Create 的图，也不改 Simurail 找轨用的那三个钩子。**它不可能让我们判"不在轨道上"。**

### 19.2 但那条路上真有一个"和谐专属"的坎：**轨型**

HeXieSimurailCompat.registerTrackType()（0.11.0 字节码）把和谐轨注册成**独立轨型**：

 + "`" + 
new TrackTypeEntry(TrackMaterialInit.HEXIE_STANDARD,        // ← 不是 STANDARD
   "simurail_track_type.hexie.standard", ..., 
   allowInverted = STANDARD.allowInverted(),

   height = 0.75,         // = surfaceHeight 默认值

TrackTypeEntries.addEntry(...)

HeXieSimurailCompat.register():
   BogeyType.setDefault(HEXIE_STANDARD, false, CW2.type())   // 和谐轨上的默认转向架 = CW2
 + "`" + 

而 indBlockTrackSegment 的筛子是

alidTypes = 转向架自己的 BogeySubtype.trackTypes()。
**转向架类型没接受 hexie:standard ⇒ 在和谐轨上永远找不到轨道 ⇒ 正好就是我们判"不在轨道上"。**

### 19.3 顺带一个真实的几何差（只影响外观）

StandardTrackBlock：

 + "`" + 
getShape / getInteractionShape / getCollisionShape  =  super.getXxx(...).move(0, heightIncrease(material), 0)
heightIncrease(m) = 0.4074 + CreateRailwayBackend.surfaceHeight(m) - 0.75
surfaceHeight(m)  =  RailwayDefinition.railSurfaceHeight()，未定义时 0.75  ⇒  默认 +0.4074
 + "`" + 

而 getElevationAtCenter 仍是原版 ⇒ Create 图里的轮轨面比和谐实际轨面**低 0.4074**。
我们不做碰撞、也不读高度，所以对我们只有外观影响；记下来是因为
Simurail 的竖直容差只到 **+0.375**，和 0.4074 是同一个量级，将来若报"某高度上找不轨"要想到这 0.03。

### 19.4 1.2.2 做了什么（只加取证，不改判定）

physicalOnTrack() 第一次判假时（注销前的第一个确认拍）打一遍轨型账：

 + "`" +

 + "`" + 

一眼能看出三件事：哪根轴丢轨、转向架接受哪些轨型、脚下这条轨是什么轨型。

### 22.5 1.3.1-diag 加了什么（`BogeySteering`）

1. `realCandidates()`：复制轴的 `TravellingPoint` 放到边末尾 0.05m，让 **Create 自己** travel 0.1m，

2. `describeCandidates()`：直/弯 + 长度 + turn 值 + 左右。
3. `describeSteerPick()`：**逐行复刻** `PhysicsBogeyAxle.steer()`，用我们当前的 `side` 算"它会挑哪条"。
4. 过节点日志扩成

5. `logCurrentPath()`：**反射读 `PhysicsBogeyAxle.currentPath`**（protected），打每个节点位置，

6. `feedPath` 只在 **dest 变了** 时打日志（不再 one-shot），并且先校验目标边与当前边**真的共节点**，

7. `clearPath` 加了原因参数，并且只有**真的清掉了一条非空路径**才打 `[path] … 清空 currentPath（原因）原内容=[…]`。
8. **自校准加前提**：只有 `st.hadCurve`（岔口确实有弯候选）才允许翻 `frameFlip`；

### 22.6 判读口径

- 走错那次的 `steer会选[X]` **等于** `实际上了` → 是 `steer()` 挑的 → 走 B 方案（改准入判据 / 改舵值）。
- `steer会选[X]` **等于** `想要` → `steer()` 本来是对的 → 根本没轮到它 → 是 `navigate()` 取候选第一条 → 走 A 方案。
- `currentPath=[J]`（且 J 就是刚到达的节点）→ 直接确认 A。
- `currentPath=[⚠旧对象]` → 图重建后 path 里的节点失效，`navigate()` 永远匹配不上。

### 22.7 第一轮取证结论（1.3.1-diag，19:39–19:56，62 次过岔）

**坐实的（不依赖探针的）**

1. **6 次走错，`当时舵` 全是 0。** 舵值全程没参与 ⇒ 不是符号问题。
2. **`不共用节点` = 0** ⇒ `feedPath` 的 `dest` 永远是合法的远端节点，"喂假 dest"这个假设死掉。
3. **没有任何 `⚠旧对象`** ⇒ 节点身份有效，`path 被图重建废掉`这个假设死掉。
4. **6/6 走错时，实际走上去的那条边 = 未过滤候选表的第一条**：
   - `19:55:41.997` `实际=弯48.45m ｜ 想要=直16.00m ｜ 舵=0 ｜ 真候选[弯38.56m(右) ｜ 直14.00m] ｜ steer会选[直14.00m]`，
     未过滤表 `弯48.45m ｜ 直16.00m ｜ 直2.00m` → 走的是**第一条**。
   - `19:54:57.747` 同样：`实际=直16.00m ｜ 想要=直5.00m`，未过滤表 `直16.00m ｜ 直16.00m` → 第一条。
5. `steer()` 复刻在那一刻会选 **直14.00m**（正确方向），实际却走了弯 ⇒ **根本没轮到 steer，是 `navigate()` 在决定**。
6. `navigate()` 只有在 `candEdge.node1 != first && candEdge.node2 != second` 对**全部**候选恒 false 时才会吐第一条；
   而"从岔口节点出去的每条边 `node1` 都等于那个节点"，所以**只要喂进去的 dest 正好等于即将到达的岔口节点，就必然退化**。
   走错时 `currentPath` 只有一个节点（如 `[(16.0, 63.0, 15.5)]`），与该退化条件完全吻合。

⇒ **结论 A 成立：`currentPath` 慢一条腿，`navigate()` 退化成"取候选第一条"。**
根因是把 `feedPath` 排在 `hold`(3 拍) / `locked`(10 拍) 的早退**之后**：2 米那条腿只要 6 拍，整段都被盖住，
path 一直停在上一腿的 dest 上。**这也解释了"上一个岔右拐、下一个岔也跟着右拐"——它其实不是跟着拐，
而是在这个岔口上固定取第一条，看起来像。**

**探针本身的 bug（已修）**

首轮 `realCandidates` 一律从 `len-0.05` 往前推，但轴可能走在**反相的那条 `TrackEdge`** 上，
于是探针跑去了"刚走过的那个岔口"。证据：62 次里只有 6 次候选含"想要"那条。
改成**按几何判定远端**（比较轴当前位置到 `edge.node1` / `node2` 的距离），1.3.2-diag 起生效。
`dumpCandidates` 也补了每条候选的远端节点，方便跟 `currentPath` 直接比对。

### 22.8 1.3.2-diag 的四处改动

| # | 改动 | 依据 |
|---|---|---|
| 1 | `feedPath` 提到 `hold`/`locked` 早退**之前**，每拍都喂；锁只管舵值不管 path | 22.7 结论 A |
| 2 | `realCandidates` 探针方向按几何判定 | 22.7 探针 bug |
| 3 | `dumpCandidates` 加每条候选的远端节点 `→(x, y, z)` | 便于和 `currentPath` 对账 |
| 4 | 自校准再加前提 `st.side != 0 && st.hadCurve` | 舵=0 时符号不可能起作用，翻了就是污染 |

## 23. 连续岔道：按"预置走法 + 每轴只选一次"重构（1.4.0-diag，2026-11-23）

### 23.1 用户定调（推翻我前面的错误方向）

1. **"每个轴单独判断"是因为有连续道岔才必须的**，它是前提，不是可疑对象。
   我一度去查"两根轴不同步"，方向错了，已撤回。
2. **"不要算腿长。转向架只要在岔口上选对了弯，就不用再管了。"**
   —— 一旦轴落到那条边上，轨道自身就把它约束住。所以 `hold` / `locked` / 腿长判断是多余的，
   而且按腿长调的窗口在连续岔道上必然盖住下一个岔口（锁 10 拍 = 500ms，2 米腿只要 7 拍）。
3. **"预缓存先预设好该怎么走道岔，到地方再逐轴精密判定，每个轴只在岔口选一次。"**

### 23.2 改了什么

**A. 删掉整套"按时间/腿长保持"的机制**
`HOLD_TICKS`、`st.hold`、`st.locked`、`remain <= 3.0 ⇒ locked = 10` 全部移除。

**B. 真正逐轴**
`tickOne` 现在对 `getAxle(true)` 和 `getAxle(false)` **各算一次**：各自读自己的 `trackPoint`、
各自算"自己这个岔口该走哪条边"、`setCurrentPath` **各写各的**。
以前是把前轴算出的 `dest` 同时写给后轴 —— 连续岔道上两根轴分处两条边，后轴那个岔口等于没被表达过。
（这就是"复制粘贴"，我认。）

**C. 预缓存里把走法定死**
`RailCache.Leg` 新增两个字段：`exitNode`（这一段从哪个节点离开）、`nextEdge`（接着走哪条边），
由新增的 `Route.planTurnouts()` 在**建路线时**填好（`buildRoute` / `assemble` 末尾各调一次）。
运行期每根轴只做：查自己那段的 `leg` → `dest = nextEdge` 的远端节点 → 喂 `currentPath`。

好处：
- "这个岔口走哪一股"不再依赖"当前边在路线里排第几"，也不再每次现推共享节点；
- 短腿上根本不需要时序窗口——每根轴在自己的岔口查一次表就够；
- 满足"上对了就不用管"：之后 `navigate()` 拿到正确远端节点，轨道自己约束。

**D. 舵值仍是转向架级一个三态值**
两根轴同时都要值时，取**本段弧长 s 更大**（更靠前、离自己岔口更近）那根轴的判定。
这是 Simurail 接口的硬限制，`steer` 只作为 `currentPath` 表达不了时的兜底。

### 23.3 仍然成立的已知限制

- `Route.legOf()` 用"无序节点对 + 首次匹配"。同一段短线在路线里出现两次（环线/灯泡线）时，
  第二趟会取到第一趟那一段的计划。当前线路不触发，但不算解决。
- `frameFlip` 自校准仍是**每位置一个位**（不是每轴一个）。两根轴符号要求相反时表达不了。
- 撕裂不可逆：短腿上一旦错一股，`RailSearch` 会 `第 1 根算不出弧长`，抱闸停死，不会自愈。
