## 1. 铁律：不可违反（违反过的都见 VIOLATIONS.md）

| # | 铁律 | 具体含义 |
|---|---|---|
| 1 | **镜像归镜像、导航归导航** | ScheduleMirror 只负责把 Create 时刻表读成我们的游标；导航/驱动是另一层。两层不许互相塞逻辑。 |
| 2 | **不让 Create 决定运动** | 它的导航我们不用（不调 `startNavigation`/`startCurrentInstruction`）。`train.speed` 由 mixin 压 0，物理速度由 `TrainSpeedInjectMixin` 注入。**这条只约束"谁决定运动"，不约束"能不能碰它的状态"。** |
| 2b | **但它的状态我们可以直接改** | `Train`/`Carriage` 的 `invalid`/`derailed`、车厢 `TravellingPoint`、运行时字段——目标需要就直写、直调。**不需要它同意，也不需要走它的流程**。 |
| 3 | **不写 Schedule 对象** | 只通过 `AllDataComponents.TRAIN_SCHEDULE` 写 `CompoundTag`，绝不构造 `Schedule` 实例塞进去。 |
| 4 | **不用 `Navigation.findPathTo`** | 已判定：除 Create 自家车外基本没有可用性。路径规划是我们自己的活。 |
| 5 | **不用 TrackEdge 对象身份当链路身份** | `connectNodes` 为每段物理轨道造**两个有向 TrackEdge**。判断"同一段轨"必须用无序节点对（`RailCache.sameLink`）。 |
| 6 | **不把 `getLocationOn` 当归属检查** | 它对任何 edge 都返回一个数（`isPrimary(edge.node1) ? len-pos : pos`）。判归属只能用 `CreateApi.hostsPoint`。 |
| 7 | **到站判定自己判断**（2026-11-16 契约变更） | 解耦/虚拟车那套已删，没有消费者需要 Create 的边点回调。到站 = 弧长距站 `|d| ≤ ARRIVE_TOL` **且** `v < V_ARRIVE`，用我们自己的制动代码停住。**边点只用于信号**（`SignalBoundary` 是唯一可知渠道）。此条覆盖 `VIOLATIONS.md` 的 V4/V7/V8 —— 那是用户决定，不是回退。 |
| 8 | **到站不许 `train.speed = 0`** | 见 V8。停车靠输出抱闸 + 物理体自己停。 |
| 9 | **信号仍走边点**，到站不再走边点 | 信号没有别的可知渠道，必须用 `EdgePointWatch.probe` + `SignalProbe`；到站见铁律 7。两套判据**故意不同**，不要再"统一"。 |
| 10 | **不要乱兜底** | "这个兜底不可信"、"兜底一般都是闯祸"。规划失败就报失败，不许拿反方向/绕环/猜站点顶上。 |
| 11 | **只留一套实现** | 不做补丁式治症状；同一件事不许有两个并行的算法。 |
| 12 | **不猜，先看日志/代码再改** | 每改一处必须能指到日志证据或源码事实。 |
| 13 | **"单向"= 单端起点，不是物理单向**（2026-11-16 实测跑通） | 搜索只从**本车**出发（不再做"车正向 + 站准入端反向"两头对撞求 F∩T，那个做不出来）；但**两个初始方向同时入队**，岔口/支线随便走。车**可以往返跑**：路线要走反方向时换另一个驱动面（换向器反相）。**永远不要**把它理解成"车只能朝一个物理方向开"或"不试反方向"。 |
| 14 | **THROTTLE 是单向指令输出** | 输出给调度器外接转速器械，**不需要回馈闭环**。但必须**曲线加速**（随距离/时间平滑爬升），不许阶跃。 |
| 15 | **空频率也是信号** | Redstone Link 的空频率是合法频道，别当"没配置"。 |
| 16 | **Create 是数据源，不是权威** | 我们拿它的数据，是因为**我们算不出来**（轨道图节点/边几何、`TravellingPoint` 在边上的位置、边点、信号状态、时刻表结构）——**不是因为它更准**。同时它的状态机/导航流程对我们没有约束力：它不给我们做的（比如把车重挂回轨道），我们直接改它的东西自己做。 |

## 2. 已证实的 Create 6.0.10 API 事实（别再重查）

反编译手段：`C:\Users\PC\AppData\Roaming\.minecraft\runtime\java-runtime-delta\bin\javap.exe`，jar 在 `H:\hf\lib\create-6.0.10.jar`。

1. `TrackGraph.connectNodes` 给每段物理轨造**两个有向 TrackEdge**：`edgeA(nodeA→nodeB)` 进 `connectionsByNode[nodeA]`，`edgeB(nodeB→nodeA)` 进 `connectionsByNode[nodeB]`。
2. `getConnectionsFrom(n)` **只返回 `node1 == n` 的出边**；`putConnection` 只写一侧。**没有反向索引**。
3. `TrackEdgePoint.getLocationOn(edge)` 不检查归属（见铁律 6）。
4. `isPrimary(node)` 的真身是 `edgeLocation.getSecond().equals(node.getLocation())` ⇒ **站点的准入节点 = edgeLocation 的第二个节点**；驶入边 = `connections(edgeLocation.first).get(edgeLocation.second)`。
5. `TrackEdge.canTravelTo(other)` = `this.getDirection(false)·other.getDirection(true) > 0.875`（≈29°），**纯几何**。
6. `getDirection(b)` 两个 b 都返回**行进方向 node1→node2**（只是取样点不同）；反向通行必须取负。
7. `RedstoneLinkNetworkHandler` **没有 tick()**；强度只在 `updateNetworkOf` 被调用时重新广播；`IRedstoneLinkable.getTransmittedStrength()` 是拉取式的活值。
8. `Schedule.cyclic` 是 public boolean（原 `ScheduleMirror` 忽略它，现已读取）。
9. `SignalProbe.observe(SignalBoundary, TrackNode enteringNode, Train)` → `Obs(signal, group, primary, chained, state)`；`State ∈ {CLEAR, BLOCKED, UNKNOWN}`。
10. `Carriage.getLeadingPoint() / getTrailingPoint()`；单节车厢只跨一条边，车头/车尾是**方向相反的两个对象**。
11. **车头点定义"前进方向"：车头 `position` 增大 = 车在前进**（朝 `head.edge.node2`）。这条由 2026-11-16 20:05 日志反证过，见 §6。
12. 20 tick/秒；`driveTick` 决策周期 5 tick = 0.25 s。
13. **道岔 = `Train.manualSteer`（`TravellingPoint.SteerDirection`：NONE/LEFT/RIGHT）。** `Navigation.control(point)` 在 `destination==null` 时返回 `point.steer(train.manualSteer,(0,1,0))`，这是岔口**唯一**的决策通道；Create 没有 TrackSwitch、没有岔位状态。`manualTick` 是它的同伴（每个 tick 会被 `tickPassiveSlowdown` 自动清掉，得每 tick 重设）。全链路见 §6.7。
14. `Train.tick` → `Carriage.travel(level, graph, dist, prevCarriageTail, nextCarriageHead, which)`；`control()` **只**给本车最前那个点（`var31==null`，即 `carriages.getFirst().getLeadingPoint()`），其余点全是 `follow()`，跟着已走过的轨迹走。

## 4. 导航五步契约（设计契约，不可改顺序）

1. 按时刻表当前 entry → 缓存这一段：路线的有向边序列 + 沿途边点（站点/信号机：弧长 s、EdgePoint 对象、所在边）
2. 用缓存边点 + 物理车位置 → 双向沿途搜索 → 得到轨道集合
3. 判定目标相对车头的方向 + 距离 → 刷新 UI「距站」（只在到站段显示数字）
4. 驱动车辆（面锁存：认证一次后锁死，到站前不再换面）
5. 依据边点触发停车（信号机 / 到站）⇒ 停车后刷新导航（回到步骤 1）

约束：一站一站来；②③只读①的缓存，不另建路；**驱动层只读缓存，不规划，一段只规划一次**。

驱动阶段机：`行驶 → 滑车 → 刹车 → 到站`；循环/不循环由 `Schedule.cyclic` 决定（`myEntry` 只在 cyclic 时回绕）。

速度控制（两份共用**同一个**「曲线速度」，双向一致）：

```
a  = train.acceleration()
vT = max(0.4, min(V_CRUISE_MPS, sqrt(2a * max(0, d - 0.5))))
dv = vT - v
dv > +DV_BAND  → 加油门
|dv| <= DV_BAND → 滑车
dv < -DV_BAND  → 刹车 max(15 * (-dv) / DV_FULL, brakeFloor)      // 急刹也是递增的，不是摁死
```

制动/到站两条链**故意分开**：减速用缓存弧长 `d = route.stationS - sNow`；到站用 Create 原生边点监听，窗口 `max(0.6, v*0.25 + 0.5)`（必须覆盖一拍行程，否则高速整帧跳过）。
到站需 **边点命中（对象身份 `atPoint.point == route.target`）+ `v < V_ARRIVE`** 同时成立；高速命中只重刹不latch。
`d < 0` ⇒ `holdOutputs()` + 警告「已越过目标站 X 米，抱闸停住」，不许油门蠕动。

## 6. 站 4 段 `sNow=NaN` 死循环（已实现修复：改成面标定定方向，待实测）

### 现象（20:05 日志，entry=1 → target=4）

```
t=2   行驶中 d=93.5  v=0.57 throttle=2
t=4   行驶中 d=94.1  v=1.86 throttle=4
t=6   滑车   d=95.3  v=2.88
t=8   行驶中 d=96.8  v=2.79 throttle=1
t=10  滑车   d=98.2  v=2.93
[drive] 新段 target=4 entry=1 | ok backwards=true 距站=98.2 边数=7
[drive] 车位不在缓存路线里 sNow=NaN stationS=98.18604737999658 → 重规划   ×649（约 162 秒）
```

车停在原地：`spd=0.000`、输出全程中性、末尾 `[diag] edgeLen=1.0`（开局是 `edgeLen=16.0`）。

### 根因 A（主因）：规划选了**反方向**

`RailSearch.search()` 第 152-160 行：从车头朝 node2 搜一次、从车尾朝 node1 搜一次，**谁短用谁**。
这两个方向对单向车是**互斥**的，不能比长短。站 4 段车尾那次赢了 ⇒ `backwards=true` ⇒ 整条路线 s 轴与车实际前进方向**相反** ⇒ 车一前进 `sNow` 就变小 ⇒ `d` 单调增大（日志正是 91.5→98.9）⇒ 车头走出第一条边、进到不在 `legs` 里的那条 1 m 小边 ⇒ `legOf()=null` ⇒ `sOf` 返回 NaN。

**这就是"规划方向必须等于车的真实前进方向（车头朝 node2）"的实证**，也说明 `backwards=true` 的路由本身就是"倒着开"，对单向车一律不合法。

### 根因 B：`driveTick` 第 1241 行把点覆盖掉了

```java
1219|  TravellingPoint pt = this.routePoint(train);   // 按"哪个能映射进路线"选
1241|  pt = CreateApi.leadPoint(train);              // ← 规划完这一拍硬写回车头
1248|  double sNow = route.sOf(pt.edge, pt.position);
```

只要该段是 `backwards=true`，1241 就把 `pt` 换成车头点，`sOf` 立刻 NaN → `driveResult = null` → 下一拍重规划 → 又 NaN。**649 对 `新段`/`重规划` 就是这么来的**，而且 `neutralOutputs()` 让车一点牵引都拿不到。

### 改法（最小、不兜底）

1. `RailSearch.search()` 只按**一个方向**展开（方向由面标定给出，不再从两端挑短的）；搜不出来就 `Result.fail(原因)`，不许拿反方向顶上。**已实施，见 §6.1。**
2. `driveTick` 里 `pt` 全程用**车头点**（`routePoint` 已删），并删掉规划后覆盖 `pt` 的那一行。**已实施。**
3. 保留 `d < 0` ⇒ 抱闸报错（单向行驶下越过站就是真故障，必须叫出来）。

验收标准：`d` 从 91.5 一路**减小**，站 4 触发 `抓到边点 … 是目标=true`。

### 6.1 已实施（2026-11-16 20:24，jar 168,716 字节；等实测验收）

方向不再由搜索"挑"，改由**面标定结果**决定。三处改动：

**① `RailSearch`：先验两道，再按标定方向搜一个方向**

原来那两个方向（朝 node1 / 朝 node2）**不是用来比长短的**，它们的职责是**校验**：
> 目标车站名字必须与时刻表导航一致 + 进入方向必须与可用轨道一致，然后才允许沿 node1 或 node2 出发。
> 不然「边点」是分不清的——断头路和车站都是边，车会不管到底是哪个边点，直接开过去/开到尽头。

`search(g, train, station, expectName, towardNode2, max)` 现在按顺序硬校验，任一条不过就
`Result.fail(原因)`，**绝不换方向重试、绝不拿别的边点当目标**：

| # | 校验 | 失败文案 |
|---|---|---|
| 一 | 站点身份：`station.name` 必须 `equalsIgnoreCase(expectName)`（expectName = 时刻表当前 entry 的目标名） | `目标站名字不符：时刻表=X 站点=Y` |
| 二 | 进入方向：唯一合法驶入边是 `edgeLocation.first → second`（`isPrimary(second)` 为真），该有向边必须真实存在，且 `arrival.node1==a && arrival.node2==b`，站点位置在该边上 | `站点准入侧没有可用驶入轨道：期望 a→b` / `驶入边朝向与准入端不一致` |
| 三 | 沿标定方向单方向展开，**目标判定只认那条 a→b 驶入边**（`k.edge == arrival && k.enter == arrival.node1`） | `搜不到驶入站点的边（上限…扩张…次）` |

规划失败时 `driveTick` **抱闸**（`phaseIdle()` + `holdOutputs()`）并打印 `[drive] 规划失败，抱闸停住：<原因>`——
不许"照旧往前开"。这是"断头路和车站都是边点"那条教训的落地。

`Result.backwards` 改名 `Result.towardNode2`，`describe()` 打印 `方向=朝node2/朝node1`。

**② `TrainDispatcherBlockEntity.ensureDirection()`：实测标定**
- 只观测一件事：给某个面加一点油门后，**车头所在边上 `position` 往哪边变**。
  `position` 变大 ⇒ 朝 `head.edge.node2` 滚（`dirSign=+1`）；变小 ⇒ 朝 `node1` 滚（`dirSign=-1`）。
- 试法：先 LEFT；LEFT 推不动（`CAL_TICK_LIMIT=40` 次决策 = 10 秒，位移仍 < `CAL_MIN_TRAVEL=0.08`）就试 RIGHT；
  **两个都不动 ⇒ `[cal] 两个面都推不动 ⇒ 不驱动（不猜方向）`，冷却 `calCooldown=40` 次决策（10 秒）再试，绝不兜底。试完两面必须 `calFace` 复位成 1。**
- 标定油门 `CAL_THROTTLE=4`；标定期间不规划、不算距站。
- 静止判定**不看 `measuredSpeedMps()`**（读档瞬间它会吐假速度，日志见过 20.61 m/s），
  改看车头在边上位置连续两拍位移 < 0.02。
- 车头跨边 ⇒ 本轮作废重取基线，不拿跨边的数据算方向。
- **换车必须重标**（比较 `train.id`）；标定结果 `DirSign` / `DriveFace` / `CalTrain` 三者随 BE 一起持久化，
  读档不再重标（否则车会在站里乱动）。

**③ `driveTick` 用标定结果**
```
if (!this.ensureDirection(train)) return;      // 标定中：本拍不规划、不驱动
boolean towardNode2 = this.dirSign > 0;
TravellingPoint pt = CreateApi.leadPoint(train);
needPlan = ... || this.driveTowardNode2 != towardNode2;   // 方向变了就重规划
```

### 6.2 术语与已确认的点

**「车头跨边」是什么意思**
Create 的 `TravellingPoint` 永远挂在**一条** `TrackEdge` 上，`position` 只在 `[0, 边长]` 内。
车往前开过这条边末端时，点被搬到**下一条**边、`position` 从 0 重新开始。
所以「隔两拍取同一个 position 相减」只在**两拍之间车头还停在同一段轨上**才成立；
一旦跨边，两个 position 属于**不同坐标系**，相减是垃圾（正负都可能颠倒）。
代码里 `[cal] 车头跨边，重取基线` 就是发现 `sameLink` 不成立 ⇒ 丢弃这轮、重新取基线，
**不拿跨边的数字算方向**。正常不该出现（标定油门 `CAL_THROTTLE=4`、窗口 10 秒、阈值 0.08 m）；
真出现说明车本来就在动，或标定油门给大了。

- 两个面都推不动：**实际不会出现**。代码里那条 `[cal] 两个面都推不动 ⇒ 不驱动（不猜方向）` 只作安全网保留。

### 6.7 道岔通道打通（2026-11-16 23:37，jar 175,618 字节）

## 10. 地雷

1. **`pantographsandwires-neoforge-1.21.1-beta-0.2.3-C6.jar`** 会在烘焙时读未绑定的 `create:wrench`（`IAgingBlock.getNext()`），导致注册表回滚 + 崩溃 `Trying to access unbound value: ResourceKey[minecraft:item / create:wrench]`。**不是我们的 mod**，别为此改代码。
